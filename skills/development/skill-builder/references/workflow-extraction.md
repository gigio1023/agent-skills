# From Real Work To A Reusable Skill

Use this when sessions, completed work, or recurring preferences are the basis for a skill. The result is a useful working method, not a transcript archive or a list of everything an agent did wrong.

## Select Evidence That Changes The Design

Start with already available, authorized task examples and analysis. Read additional source material only for a gap that affects the design; a skill improvement request does not require a fresh sweep of every session or connected workspace.

Look for the situation that triggers the work, the result the user needs, the decisions that made it useful, and the evidence that supports those decisions. Include successful artifacts, accepted explanations, and explicit preferences alongside correction sequences. Distinguish a direct user preference, an observed outcome, and the author's proposed improvement.

When reviewing session collections, account for inherited forks, forwarded requests, delegated packets, retries, and assistant paraphrases. They may explain a workflow but are not independent confirmations of a human preference. Missing attachments or uninspected sources remain coverage limits. Existing analysis can support design; return to the original only when the interpretation or evidence is consequentially unclear.

One well-understood example can be enough to start a personal or project-local skill. Say what it supports without inventing frequency or claiming measured improvement. Keep detailed private evidence locators in the authorized analysis, not in a public package or PR.

## Separate The Method From Its Context

Ask what a later agent should do differently when the same situation arises. Preserve that decision and the reason that helps it adapt. Separate three kinds of material:

| Material | Appropriate home |
| --- | --- |
| Reusable judgment, preferred explanation, fragile procedure, evidence boundary | Skill instructions and relevant references |
| Stable private project knowledge, source map, schema, approved runner contract | The owning private project or a private skill, loaded when needed |
| Current progress, credentials, raw records, run identities, changing priorities | Authorized external state or project task records, never replaceable package files; credentials remain in the existing secret mechanism |

A skill can be useful because it knows how to use a project's tools well. For example, the method may reconcile a queue with actual run evidence while an existing command provides reliable status. Do not reject the skill because a helper is necessary, or build a universal queue merely to avoid project-specific binding.

Do not turn one artifact's incidental format into a universal requirement. A timeline may resolve chronology, but not every investigation needs one. A policy-specific denominator belongs to that evaluator, not all evaluation workflows. Preserve the property and the conditions that require it.

## Choose The Owning Capability

Compare the candidate with the relevant existing skills, not the entire installed portfolio unless an audit was requested.

- Improve an existing skill when it already owns the trigger and result, including when the missing piece is a preferred judgment rather than a missing step.
- Create a skill when a distinct capability is awkward to discover or express through existing entry points. A clearly bounded personal or project-local workflow can justify one without repeated instances, failures, or cross-project adoption.
- Combine packages when one task has unnecessarily competing owners or coupled steps that are clearer together. Shared connectors or terminology alone are not a merger case.
- Compose outputs when tasks are related but independently useful: evidence can inform a proposal, and completed work can inform a shared document. Composition does not make either task automatic or broaden its authority.

When the capability boundary remains uncertain or the user requests a validation plan, identify a first real use that would demonstrate the value, such as reconstructing one project's work from incomplete records or resuming an approved evaluation from its actual results. This is a proposed application unless the user authorized running it. A simple preference skill need not add a first-use plan or a new evaluation harness to finish an instruction-only change.

## Keep Confidential Work Out Of Public Packages

Separate permission to inspect from permission to disclose. Check the destination's visibility before preparing publishable artifacts. A public skill should teach the procedure without exposing private personal details, contact information, account identifiers, company identities tied to confidential work, private URLs, customer cases, unpublished plans, internal metrics, source quotations, or combinations of details that identify the underlying work. Preserve intentional public attribution, such as a cited public author's name or the verified public forge handle; not every proper name is confidential.

Build synthetic examples from the decision to teach. Do not copy a private case and only replace its names: distinctive dates, counts, architecture, or failures can still disclose it. If abstraction would destroy necessary private semantics, leave the binding private and make the public skill ask for that authorized reference at runtime.

Inventory the intended staged, unstaged, and untracked files before reviewing publication content; an ordinary diff alone will miss new untracked resources. Inspect all intended published surfaces, not only SKILL.md: references, assets, script fixtures, generated output, filenames, symlinks, screenshots, attachments, logs, commit messages, and PR copy. Check the complete intended content and the history to be published, including Git author and committer names and emails, while preserving unrelated files outside that scope. Pattern scans can assist, but identifying personal details and confidential business facts requires content review. Do not paste private matches into the PR as evidence that the review happened.

For new public commits, use the user's approved public identity or a verified forge-provided privacy address rather than exposing a private email; do not fabricate an account or change global Git configuration. When sensitive information is already committed, a new redaction commit leaves the earlier version in history. Correct only authorized, workflow-owned history, coordinate shared branches, and use the forge's safe publication workflow. Rewriting or force-pushing a branch does not guarantee removal from old objects, forks, PR artifacts, or caches. Report the remaining exposure without repeating the sensitive value; broader history cleanup or forge support coordination requires its own scope. An exposed credential also needs a separate revocation or rotation response; history cleanup is not a substitute.

The public package may explain that it uses task-derived design principles without linking to private analysis. Do not fabricate public citations for private feedback. Keep public-source advice, local design choices, and measured results distinct.

## Learn From Subsequent Use

When the user requests iteration, compare the needed result with what actually happened. Identify the missing input, retrieval failure, preferred judgment, tool limitation, conflicting rule, or verification gap. A rule that was present but ignored calls for investigation of loading and evidence visibility before adding stronger duplicate wording.

Preserve what worked. Express useful defaults positively, retain exceptions where they affect the decision, and revise the authoritative resource instead of appending each correction to the entry point. Task-specific exceptions can stay in the project. Installed instructions are not a place for accumulating run logs.

Judge improvement by useful decisions, fewer repeated explanations, preserved evidence, and reliable completion. Package checks establish structure; script tests establish exercised software behavior; actual task feedback or requested comparisons establish behavioral evidence. A static read-through of a synthetic case is not a model trial.

This learning process does not authorize telemetry, automatic session collection, memory writes, background self-modification, publication, or installation. Carry out the maintenance and delivery actions the user requested, including already authorized local fixes and checks, without adding unnecessary review stops.
