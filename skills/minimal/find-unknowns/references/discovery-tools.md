# Discovery Tools

These tools serve the pass when the scan shows a kind of unknown that a direct question handles poorly. Use one, combine several, or switch between them within the same objective and grant. None of them is a required step, and none replaces the scan, your view, or the batched questions.

| Dominant unknown | Signal | Tool |
| --- | --- | --- |
| Unsettled direction or scope | Several materially different ways to attack the goal | Option map |
| Taste | The user can judge a result but cannot describe it in advance | Throwaway variants |
| A want best shown, not told | A comparable example exists somewhere | Reference request |
| Dependent choices | The first answers open follow-up decisions | Mini-interview |

## Option Map

Inspect the relevant code, files, or sources before proposing directions. Lay out materially different options rather than variations of one, and compare them by the trade-offs that decide between them, including cost, reversibility, and the unknown each one resolves. Keep the set small enough to compare without dropping a consequential alternative, and say which option you would choose and why. Record the options the user accepts or rejects as scope decisions in the user's own words.

## Throwaway Variants

Make a few concrete alternatives that differ on the uncertain choice, such as mockups, strawman drafts, or sample plans. Label them as throwaway and label any synthetic data. Pick a comparison format the user can judge quickly. Polish and production wiring add nothing to this decision, and a variant wired into a real system stops being throwaway. Save artifacts only within the task's file authority. Record only the preferences the user's reactions actually establish. If the user cannot say which variant is better, establish the comparison criteria first with a short explanation or a reference comparison.

## Reference Request

Reuse an example already available before asking for another. Prefer inspectable source for code and a concrete artifact elsewhere, such as a portfolio, paper, recording, contract, or finished product. Name the features that transfer, and keep three things apart: what you observed in the reference, what you propose to borrow, and what the user has decided.

## Mini-Interview

Use a short follow-up round when the answers to the first batch of questions open dependent decisions. The rules of the main pass still hold: ask only what changes the result, never what inspection can settle, give options with a recommended default, and leave unanswered items open with a decide-later rule. A question that only a measurement or trial can settle becomes an investigation item, not a question. When the exchange keeps growing past a round or two, offer `interview` instead of extending this pass.

## Comprehension Check

Run it only when the user cannot verify the result directly, as with a strategy, a recommendation, or a document judged by its readers, and wants a check. First explain the evidence, consequences, and unresolved decisions behind the result. Then pose a few short scenarios whose answers show whether the user understands the consequential decisions and the conditions under which they would change. Understanding does not establish that the result is correct and does not replace permission or professional review. The check never blocks an action that is already authorized.
